## ⚠️ 三条铁律（每次改动前必读）

### 铁律 1：这个插件不是为某一个工程写的

它是**通用串口工具**，未来服务于用户的每一个串口项目（STM32、Modbus、蓝牙模块、传感器……）。

| 必须放插件本体（通用机制） | 必须放场景配置（设备知识） |
|---|---|
| 串口收发 | 具体查询命令（`P` / `AT` / `01 03...`） |
| 定时轮询 | 具体异常判据（`FAULT` / `ERROR` / 任意） |
| 字符串/正则匹配 | 具体处置命令（`R` / `AT+RESET` / 任意） |
| 状态机 | 安全白名单 |

**验收：代码里搜不到 `"P"`、`"FAULT"`、`"CH1"`、`"stall"` 等字样。**

### 铁律 2：控制权必须真正生效

`human` / `paused` 状态下，AI **绝对不允许**发命令。这是安全底线。

### 铁律 3：不阻塞主收发流程

规则判定、日志、通知等附加逻辑，**不得影响串口收发**。出错只记日志，收发照常。

# 阶段 1：修 Bug（最高优先级）

## Bug 1 🔴 控制权形同虚设（已实测确认）

### 现象

```
control state="paused"    ← 状态是"已暂停"
ai_may_send=yes           ← 但 AI 仍然能发命令 ❌
```

实测三个状态全部失效：

| 状态 | AI 应该 | AI 实际 | 结果 |
|---|---|---|---|
| `ai` | 能发 | 能发 | ✅ 正常 |
| `paused` | **不能发** | **能发** | 🔴 Bug |
| `human` | **不能发** | **能发** | 🔴 Bug |

### 复现

```
1. serial_control(action="pause")   → 状态变 paused
2. serial_send("P")                 → 仍然成功返回 ❌ 应该拒绝
```

### 要求

`serial_send`（及所有发命令的工具）执行前**必须**检查：

```python
state = get_control_state(scene)
if state != "ai":
    raise Error(f"当前控制权是 {state}，AI 不能发命令。"
                f"需要人类在网页点[交给AI]或[继续AI]。")
```

### 安全影响

```
用户：暂停AI，我要手动操作
AI：（照样发 W 1000 1000 1000 1000）
→ 车冲出去
```

**这条不修，人机协同无从谈起。**

## Bug 2 🟡 `/control` 接口参数不一致

```
POST /control {"action":"ai"}      → 200 OK ✅
POST /control {"action":"human"}   → 400 Bad Request ❌
POST /control {"action":"pause"}   → 200 OK ✅
```

`human` 报 400，但网页按钮能用。**可能是动作名不同（如 `takeover`）或需要额外参数。**

### 要求

统一接口参数，400 时返回具体原因。

## Bug 3 🟡 状态同步延迟

```
网页点「交给AI」 → 但 serial_status 仍显示 control="human" by="init"
```

可能原因：
- 网页和插件读的不是同一份状态
- 或状态文件写入有延迟

### 要求

控制权变更后，**立即**对所有读取方可见。

## Bug 4 🔴 定时发送完全不工作（已实测确认）

### 现象

```
开启定时发送 → send_enabled=True
等 5 秒      → watch_running 始终 False
结果         → 一条命令都没发出去
```

### 复现

```
POST /watch {"send_enabled": true, "command": "P", "interval_ms": 1000}
→ 返回 ok: true，send_enabled: true
→ 但 watch_running 一直是 false
→ 5 秒内没有任何命令发出
```

### 用户反馈

> "刚才点自动发送，它也没有自动发送过内容"

### 要求

`send_enabled=true` 时，必须真正启动发送循环：

- `watch_running` 应该变 `true`
- 按 `interval_ms` 定时发 `command`
- 关闭时停止并释放

### 排查方向

- 检查 `send_enabled` 变更后有没有启动 `WatchLoop` 的 `send_thread`
- 检查 `watch_running` 状态是否只是没更新（假阴性）
- 检查是否因为串口被占导致循环启动失败但没报错

## Bug 5 🟡 light 模式仍然占用串口

### 现象

```
mode: light
watch_running: False
但 COM10 被占用（外部程序打不开）
```

### 矛盾点

代码注释写的是：

> light（默认）不长期占口：每个请求临时开口 → 读 → 关。

但实测：**网页一启动，串口就被占住**，外部程序（含 `serial_send`）打不开。

### 用户影响

- 网页开着时，串口助手用不了
- 网页开着时，AI 的 `serial_send` 可能失败

### 要求

light 模式下：

- 启动时**不打开**串口
- 每个 `/send`、`/poll` 请求临时打开→操作→**立即关闭**
- 验证方式：网页开着时，外部程序能打开同一串口

### 注意

之前测试曾出现过"不占口"的结果，后来又变成"占口"。可能是：
- 有句柄泄漏（未正确 close）
- 或某个后台线程持有了串口

## Bug 6 🟡 控制权初始状态混乱

### 用户反馈

> "刚进去的时候，切换不了人工，暂停AI之后，切换人工又能正常发送了"

### 现象

```
初始状态 control="human" by="init"
→ 点「人类接管」无效（因为已经是 human）
→ 但此时 human 状态下 AI 能不能发？行为不一致
```

### 问题

初始状态 `human by="init"` 语义模糊：

- 它是"真正的人类接管"吗？
- 还是"尚未初始化"？
- 为什么点「人类接管」没反应？

### 要求

明确初始状态语义，建议：

| 方案 | 说明 |
|---|---|
| **A. 初始为 human** | 但「人类接管」按钮应该可用（幂等，点了显示"已在你手中"） |
| **B. 初始为 paused** | 谁都不能发，需要显式切换 |
| **C. 初始为 ai** | 但要明确告知用户"AI 已获得控制权" |

**无论选哪个，按钮状态要与实际状态一致，不能出现"点了没反应"。**

## UI 问题 2 🟡 控制权/系统提示混在串口界面里

### 用户反馈

> "控制权等系统提示词不应该放在串口的界面混杂在一起，可以在对话框上方给一小块可上下滑动查看的时间轨道"

### 问题

控制权状态、系统提示等"非串口数据"的内容，和串口收发记录混在同一个区域，**信息层级不清**。

### 建议布局

```
┌─────────────────────────────────────┐
│ ★ 状态轨道（可滚动，独立区域）       │
│   10:23:01 控制权 → AI              │
│   10:23:15 串口 → COM10             │
│   10:23:30 告警 → 无响应            │
├─────────────────────────────────────┤
│ 串口收发区（纯数据）                 │
│   >> P                              │
│   STATE RUNNING                     │
│   ...                               │
└─────────────────────────────────────┘
```

**核心**：把"系统事件"和"串口数据"分成两个视觉区域，不要混在一起。

**时间轨道**：显示事件时间线（控制权变更、串口切换、告警等），可上下滚动查看历史。

# 阶段 2：AI 侧增强

> 详细设计见 `AI侧增强方案.md`，这里只列要点

## 2.1 新增 `serial_send_batch`（P0）

一次调用发多条命令，**串口只开一次**：

```json
{
  "scene": "蓝牙AT",
  "steps": [
    {"command": "A", "expect": "OK"},
    {"command": "W 500 500 500 500", "expect": "OK"},
    {"command": "P", "capture": true}
  ],
  "stop_on_mismatch": true
}
```

**价值**：多步操作从 5 次调用变 1 次。

## 2.2 新增 `serial_wait`（P0）

发完命令等设备就绪，不盲等：

```json
{
  "scene": "蓝牙AT",
  "until": {"type": "contains", "value": "OK"},
  "timeout_ms": 3000
}
```

## 2.3 `serial_status` 增强（P1）

增加关键字段：

```json
{
  "aiCanSend": true,
  "portAvailable": true,
  "portBusyBy": null,
  "blockReason": null
}
```

**AI 发命令前先查这个，避免盲目失败。**

## 2.4 结构化解析（P1）

```json
serial_send({
  "scene": "...", "command": "P",
  "parse": {"type":"regex", "pattern":"CH(\\d) T=(\\d+) A=(\\d+)", "fields":["ch","T","A"]}
})
```

**解析规则来自参数，不是插件内置。**

# 阶段 3：网页增强

## 3.1 新增 `serial_web` 工具（P0）⭐

**用户痛点**：每次开网页要自己敲命令，很麻烦。

### 要求

```json
serial_web({"scene": "蓝牙AT", "port": 8898, "action": "start"})
→ {"ok": true, "url": "http://127.0.0.1:8898", "pid": 12345}

serial_web({"scene": "蓝牙AT", "action": "stop"})
→ {"ok": true}
```

**效果**：用户说一句"开网页"，AI 直接开好并给出 URL。

### 注意

- `start` 要幂等（已开着就返回现有 URL）
- `stop` 要真正释放串口
- 不能和 `serial_send` 并发冲突

## 3.2 网页可编辑异常规则（P1）

**现状**：网页只能开关判定，规则必须手动改 `config.json`。

**要求**：加规则列表 UI + 添加/编辑弹窗，保存写回配置。

```
┌─────────────────────────┐
│ 异常判定  [开启]        │
│ 规则列表                │
│ ☑ 规则1  含"X" → 发"Y"  │
│ ☑ 规则2  无响应 → 发"Z" │
│ [+ 添加规则]            │
└─────────────────────────┘
```

## 3.3 暂停/退出分离（P1）

**现状**：只有一个「退出并释放」，点了网页就打不开。

**要求**：拆成两个：

| 按钮 | 网页 | 串口 |
|---|---|---|
| **暂停并释放串口** | 仍可访问 | 释放 |
| **彻底退出** | 关闭 | 释放 |

## 3.4 DSH 侧边栏 iframe（P2，可选）

**原理**：注册一个侧边栏面板，内容用 iframe 加载 `http://127.0.0.1:8898`。

```javascript
ctx.ui.registerSidebarPanel({
  id: 'serial-bridge',
  title: '串口桥',
  render: () => h('iframe', { src: 'http://127.0.0.1:8898' })
})
```

**前提**：服务要能常驻（配合 3.1 的 `serial_web`）。

**参考实现**：`%USERPROFILE%\.dsh\profiles\web\node_modules\dsh-better-sidebar`（大型示例）

## 3.5 占用者提示（P2）

串口被占时明确显示是谁占的：

```
COM10  [被本网页占用]
COM10  [被其他程序占用]
COM10  [可用]
```

## 给开发者的话

**每次改动前问自己三个问题：**

1. 这个改动会让"换一台设备"需要改代码吗？→ 会，就设计错了
2. 控制权失效了吗？→ 失效，就违反安全底线
3. 附加逻辑会阻塞收发吗？→ 会，就违反了铁律 3

**按阶段来，不要跳。** 阶段 1 的 bug 不修，后面所有功能都建立在不可靠的地基上。
