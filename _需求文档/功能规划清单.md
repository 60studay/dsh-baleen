# 阶段 2：AI 侧增强

## 为什么优先做 AI 侧

| 对比 | 网页端 | AI 端 |
|---|---|---|
| 谁在用 | 用户偶尔看 | **AI 每次调试都调** |
| 调用频率 | 低 | 高 |
| 现状 | 已比较完善 | **还很基础** |
| 优化收益 | 体验提升 | **直接影响能否做成事** |

**核心痛点**：AI 做多步操作（如调 PID）需要连续多次调用，每次都要开关串口、等待、解析，效率低且易错。

## 2.1 新增 `serial_send_batch`（P0）

### 问题

发 5 条命令 = 5 次工具调用，每次都要开串口→发→等→关。

### 要求

一次调用发多条命令，**串口只开一次**：

```json
{
  "scene": "蓝牙AT",
  "steps": [
    {"command": "A", "expect": "OK", "timeout_ms": 1000},
    {"command": "W 500 500 500 500", "expect": "OK"},
    {"command": "P", "capture": true}
  ],
  "stop_on_error": true,
  "stop_on_mismatch": true
}
```

### 参数

| 参数 | 说明 |
|---|---|
| `command` | 要发的命令 |
| `expect` | 可选，回显不含此串则失败 |
| `timeout_ms` | 该步超时 |
| `capture` | 是否保留完整回显 |
| `stop_on_error` | 出错即停，默认 true |
| `stop_on_mismatch` | 期望不匹配即停，默认 true |

### 返回

```json
{
  "completed": 3,
  "total": 5,
  "stopped": true,
  "stopReason": "mismatch",
  "steps": [
    {"index": 0, "command": "A", "response": "OK RUNNING", "ok": true, "matched": true}
  ]
}
```

### 关键要求

- **串口只开一次**，整个批次复用
- 失败可定位（`completed` / `stopReason` / 每步 `ok`）
- **不影响 `serial_send`**（两者并存）
- 每步间可配间隔 `gap_ms`（默认 100ms）

## 2.2 新增 `serial_wait`（P0）

### 问题

发完命令就返回，不知道设备何时就绪，AI 只能盲等。

### 要求

```json
{
  "scene": "蓝牙AT",
  "until": {"type": "contains", "value": "OK"},
  "timeout_ms": 3000,
  "poll_command": "P"
}
```

### 判据类型（与规则引擎一致）

| type | 说明 |
|---|---|
| `contains` | 收到含某字符串的数据 |
| `regex` | 正则匹配 |
| `equals` | 完全等于 |
| `silence` | 线路安静 N 毫秒 |

### 返回

```json
{
  "satisfied": true,
  "elapsed_ms": 850,
  "attempts": 3,
  "matchedData": "OK RUNNING",
  "timedOut": false
}
```

## 2.3 `serial_status` 增强（P1）

### 现状

信息有限，AI 发命令前无法判断"现在能不能发"。

### 要求增加字段

```json
{
  "aiCanSend": true,
  "portAvailable": true,
  "portBusy": false,
  "portBusyBy": null,
  "blockReason": null,
  "consecutiveFailures": 0,
  "lastSendAt": "2026-11-04T22:30:00"
}
```

### 关键

`aiCanSend` 是综合判断，AI 发命令前先查这个，避免盲目失败。

## 2.4 结构化解析（P1）

### 问题

`response` 是整段文本，AI 要自己解析。

### 要求

```json
serial_send({
  "scene": "蓝牙AT",
  "command": "P",
  "parse": {
    "type": "regex",
    "pattern": "CH(\\d) T=(\\d+) A=(\\d+) O=(-?\\d+)",
    "fields": ["ch", "T", "A", "O"]
  }
})
```

### 返回增加

```json
{
  "parsed": [{"ch": 1, "T": 500, "A": 498, "O": 312}],
  "parseError": null
}
```

### 关键

- **解析规则来自参数**（不是插件内置）
- 解析失败不影响 `response` 原文

## 2.5 并发重试（P2）

连续调两次 `serial_send` 时，第二次可能因第一次未关串口而失败。

### 要求

```
尝试打开串口
失败且原因是"被占用"
  → 等 200ms 重试
  → 最多 2 次
  → 仍失败才报错
```

# 阶段 3：网页增强

## 3.1 新增 `serial_web` 工具（P0）⭐

### 用户痛点

> "感觉要开启网页版调试窗口有点困难，不能我提到你就直接打开吗？"

每次开网页要自己敲命令。

### 要求

```json
serial_web({"scene": "蓝牙AT", "port": 8898, "action": "start"})
→ {"ok": true, "url": "http://127.0.0.1:8898", "pid": 12345}

serial_web({"scene": "蓝牙AT", "action": "stop"})
→ {"ok": true}
```

### 关键要求

- **`start` 必须幂等**：已开着就返回现有 URL，**不要重复启动**
  - 实测踩过坑：重复启动导致两个进程抢串口
- `stop` 要真正释放串口
- 不能和 `serial_send` 并发冲突

---

## 3.2 网页可编辑异常规则（P1）

### 现状

网页只能开关判定，规则必须手动改 `config.json`。

### 用户反馈

> "我发现异常，判定没有给我写处理问题的地方"

### 要求

加规则列表 UI + 添加/编辑弹窗，保存写回配置：

```
┌─────────────────────────┐
│ 异常判定  [开启]        │
│ 规则列表                │
│ ☑ 规则1  含"X" → 发"Y"  │
│ ☑ 规则2  无响应 → 发"Z" │
│ [+ 添加规则]            │
└─────────────────────────┘
```

---

## 3.3 暂停/退出分离（P1）

### 现状

只有一个「退出并释放」，点了网页就打不开。

### 要求

拆成两个：

| 按钮 | 网页 | 串口 |
|---|---|---|
| **暂停并释放串口** | 仍可访问 | 释放 |
| **彻底退出** | 关闭 | 释放 |

## 3.4 DSH 侧边栏 iframe（P2，可选）

### 原理

注册一个侧边栏面板，内容用 iframe 加载网页：

```javascript
ctx.ui.registerSidebarPanel({
  id: 'serial-bridge',
  title: '串口桥',
  render: () => h('iframe', { src: 'http://127.0.0.1:8898' })
})
```

### 前提

服务要能常驻（配合 3.1 的 `serial_web`）。

### 参考实现

`%USERPROFILE%\.dsh\profiles\web\node_modules\dsh-better-sidebar`（大型示例）

### 注意

iframe 里的内容依赖网页服务存活，服务停了就是空白页。

# 阶段 4：场景提示词

## 4.1 新增 `prompt.md`（P1）

### 要解决的问题

`protocol.md` 说"设备能做什么"，但**没说"用的时候该注意什么"**。

新会话的 AI 不知道操作纪律，可能犯同样的错。

### 位置

```
protocols\<场景>\
├── config.json
├── protocol.md
└── prompt.md      ★新增
```

### 三个文件的分工

| 文件 | 内容 | 性质 |
|---|---|---|
| `config.json` | 串口参数 | 机器可读 |
| `protocol.md` | 命令表、返回值、踩坑 | **参考手册** |
| `prompt.md` | 操作顺序、前置条件、禁忌 | **行为约束** |

### 示例内容

```markdown
# 蓝牙AT 操作提示

## 前置条件
- 发运动命令前必须先发 A 启动
- 未启动时发 W 会返回 ERR NOT RUNNING
- 桌面测试必须架空轮子

## 安全限制
- 首次调试速度不超过 500
- 单次运行不超过 30 秒

## 禁止操作
- 不要跳过 A 直接发 W
```

### 实现要求

- `serial_info` 返回时一并带上 `prompt` 字段
- 文件不存在时 `promptMissing: true`，不报错
- **原样返回，不解析、不替换、不合并**

| 保留备份/能回滚 | 删掉旧代码 |
| 保持通用性 | 引入设备专有逻辑 |

1. `supervisor.py` 按职责拆成 3-4 个文件
2. `index.html` 的 CSS/JS 抽成独立文件
3. 每步跑 `selfcheck_*.py` 验证
