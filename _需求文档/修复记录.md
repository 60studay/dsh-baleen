## 二、逐个说明

### Bug 2 · `/control` 400

`human` 一直是合法动作名。真正的原因是：状态已经是 `human` 时，`human → human`
被迁移表判为非法，于是 400；而 `human → ai` 合法，所以看起来"只有 ai 能用"。

**改法**：目标状态与当前相同就直接成功（幂等），返回
`200 {"note": "已经是人类接管，无需切换"}`。真正非法的方向（human 点暂停/继续）仍然 400。

### Bug 3 · 状态不同步（本轮最隐蔽的一个）

实测两处状态文件并存：

```
<你的日志目录>\.runtime\state\蓝牙AT.json   ← 插件进程写
<插件目录>\logs\.runtime\state\蓝牙AT.json      ← 手动启动网页写
```

`cli.py` 的 `_paths()` 只认环境变量；环境变量是插件注入的，用户自己开终端启动网页时没有，
于是退回 `BASE/logs`。两个进程各写各的。

**改法**：`log_root` 写进插件自带的 `config.json`，`_paths()` 按
`env > config.json.log_root > BASE/logs` 解析；`index.js` 也读同一个键。
两边落到同一份 state。`/status` 新增 `state_path` 字段，便于以后排查。

### Bug 4 · 定时发送不工作

发送循环原来在 `WatchLoop._send_loop`，而 `WatchLoop` 只在"监视模式 + 控制权 ai"时启动。
light 模式下把 `send_enabled` 打开：`watch_running` 永远 false，一条也不发，也不报错。

**改法**：搬到 `WebServer._autosend_loop`，独立线程，两种模式都跑：
- 监视模式（持有句柄）→ 直接写句柄
- 轻模式（不持有）→ 临时开口发一条再关
- `paused` 时跳过（paused 语义是"谁都不发"）
- 发送失败只记 `autosend_error`，线程不退出

`watch_running` 语义改为"后台自动循环是否在跑"，另加 `port_held` 表示是否真的持有句柄。

### Bug 5 · light 模式占串口

`/poll` 每 700ms 调一次 `drain()`，每次最多等 1500ms 首字节 → 串口几乎一直开着。
另外 `/status` 里的占用探测（`port_owner`）每次也都开一次口。

**改法**：
- 轻模式 `/poll` **默认完全不碰串口**，直接返回 `skipped`
- 需要时点网页上的 **「读一次」**（`/poll?force=1`）才真正读一帧
- `port_owner` 探测结果缓存 5 秒，状态栏不再自己占口

代价：轻模式下设备主动上报的数据看不到——本来就这样（要看连续流请切监视模式）。

### 排查经验：无回显先发 `AT` 判模式

本轮真机卡住时的关键经验（已写进 `protocols/蓝牙AT/protocol.md` 第七节）：

| 步骤 | 操作 | 判读 |
|---|---|---|
| 1 | 发 `AT` | 回 `OK` → 主机卡在 AT 模式，没进透传 |
| 2 | 发 `AT+RESET` | 回 `OK` |
| 3 | **关闭串口**，等 **20 秒** | 让它自己连从机 |
| 4 | 发 `AT+STATE?` | `CONNECTED` 通了 / `CONNECTING` 从机没上线 |

- 回 `ERR STATE` → `AT` 已被转发给底盘，链路其实是通的，直接发底盘命令
- 完全没反应 → 才轮到查波特率/接线/供电

**不要只查波特率和接线。** 这段设备知识放在场景配置的 `no_response_hint` 里，
插件"无回显"时会直接提示出来；代码里没有 `AT` 字样，通用性不受影响。

## 五、Bug 4 修正：不是"不发送"，是"网页看不到"

> 2026-11-05 12:20 更新。原判定"定时发送完全不工作"不准确——后端一直在发，
> 是网页回显区拿不到数据。用户说的"没看到"≠"没发送"。

### 根因

`poll()` 的条件是 `mode == "watch" and loop.running`。light 模式下 `loop.running`
永远是 False（`WatchLoop` 只在监视模式启动），所以走 `skipped` 分支，永远返回空。

**另有一处更根本的问题**：light 模式的自动发送走 `transact()`，
回显只写进了日志，**根本没进缓冲区**，所以光改判断条件也取不到。

### 为什么没照搬"改成 `loop.running and loop.has_data()`"

那个条件在 light 模式下依然是 `False`——`loop.running` 只在监视模式为真，
改完等于没改。而且 `has_data()` 并不存在。

### 实际改法

1. `send_raw()` 每发一帧（不论模式）都往 `auto_frames` 记 `{tx, rx, hex, bytes, ts}`
2. `poll()` **不分模式**先把 `auto_frames` 和缓冲区取走
3. 前端渲染 `frames`：先打 `>> 命令`，再打回显（和手动发送同一套显示）

### 验证

真机（light 模式，`P` / 1000ms），模拟网页 700ms 轮询：

```
>> P  回显 99 字节: STATE RUNNING
>> P  回显 99 字节: STATE RUNNING
>> P  回显 99 字节: STATE RUNNING
>> P  回显 99 字节: STATE RUNNING
```

自测 `selfcheck_autosend.py` 新增 `[2b]`：poll 能拿到帧、帧里带命令和回显、
取走后不重复投递。现为 **14 项**。

## 六、Bug 7 / Bug 8（2026-11-05 12:45）

### Bug 7 异常判定不触发

**不是 poll 的问题，也不是"和 Bug 4 同源"。** 两个独立原因：

**① 手动发送根本没调用判定。**
`WebServer.send()` 拿到回显后直接返回，从来没调 `_run_checks`。
监视模式下回显走读线程、被标成 `watch`，`check_source=manual_only` 也会失效。

改法：`send()` 返回前调 `_maybe_check(rx_text, "manual")`；
监视模式下手动发送会打一个 2 秒窗口标记，读线程据此把来源标成 `manual`。

**② 故障是异步上报的，被读取窗口截断了（真机实测）。**

```
442 ms  OK 4 TARGETS
866 ms  [FAULT] stall mask=15  send R to reset   ← 晚 424ms
```

原来 `quiet_ms=200`，读完第一段就判定"收完了"并关闭串口，FAULT 根本没读进来，
自然没有可判的内容。把 蓝牙AT 场景的 `quiet_ms` 调到 600，覆盖这个间隔。

> 这也解释了"为什么日志里能看到 FAULT，但 alerts 是空的"——日志是分两次写的，
> 而判定只拿到第一段。

真机验证：

```
R → OK RESET     A → OK RUNNING
W 1000×4 → 55 字节（含 [FAULT] stall）
alerts: 1 条 —— 规则「堵转保护触发」命中 → R sent=True
```

### Bug 8 AI 发的命令网页看不到

按方案 B：网页在跑时 AI 的命令统一走它的 `/send`。

- `cli.cmd_send()` 先查同场景的网页实例（`.web.json`），在跑就 POST `/send`
- 网页把 AI 发起的命令记成一帧（`source="ai"`），前端显示 `[AI] >> P`
- 网页没跑 / 不可达 → 自动回退到直接开串口，不报错
- 网页返回的业务错误（如 `control_blocked`）原样透传给 AI

真机验证：

```
CLI: ok | port_source=web | note=已交给网页发送 | bytes=96
/poll: source=ai  >> P  回显 96 字节
       source=auto >> R  回显 10 字节   ← 规则自动处置也一并可见
```
