## ⚠️ 铁律（改代码前必读）

### 铁律 1：不是为某一个工程写的

插件是**通用串口工具**，服务于所有串口项目。代码里**不允许**出现具体设备的命令字。

| 必须放插件本体 | 必须放场景配置 |
|---|---|
| 串口收发、轮询、匹配 | 具体命令（`P` / `AT` / `01 03...`） |
| 状态机 | 具体故障字（`FAULT` / `ERROR`） |
| 错误处理 | 具体处置命令（`R` / `AT+RESET`） |

**验收：代码里搜不到 `"P"`、`"FAULT"`、`"CH1"`、`"stall"`。**

### 铁律 2：控制权必须真正生效

`human` / `paused` 状态下，AI **绝对不允许**发命令。

### 铁律 3：不阻塞主收发

规则判定、日志等附加逻辑出错，只记日志，收发照常。

## 🧩 关于"AI 被卡死"的说明

### 现象

测试过程中，AI 调用 `serial_send` 反复失败，报"COM10 被其他程序占用"。

### 根因

**这不是独立 bug，是 Bug 5 的直接后果：**

```
网页进程（light 模式）→ 实际占着 COM10
                        ↓
AI 的 serial_send → 打不开串口 → 报错 → 看起来像"卡死"
```

### 附带发现

| 现象 | 性质 |
|---|---|
| 两个网页进程同时运行，互相抢串口 | 🟡 **设计缺陷**：`serial_web` 必须幂等（阶段 3 要求） |
| 关进程后串口延迟几秒才释放 | 🟢 正常（Windows 句柄释放有延迟） |

**结论**：修好 Bug 5，卡死问题自然消失。

## Bug 4 🟡 定时发送在网页上看不到（后端正常，前端不显示）

> **2026-11-05 重新实测，修正描述**：之前判定"完全不工作"是错的。
> 后端发送正常，问题在前端不显示。

### 实测证据

开启定时发送（`P`，1000ms）后，查看 `log.txt`：

```
[12:12:40] TX P    → RX STATE IDLE ...
[12:12:42] TX P    → RX STATE IDLE ...
[12:12:43] TX P    → RX STATE IDLE ...
[12:12:44] TX P    → RX STATE IDLE ...
```

**后端确实在按间隔发送，底盘也回应了。**

同时 `/status` 返回：

```json
{"send_enabled": true, "watch_running": true}
```

状态也是对的。

### 真正的问题

**网页的回显区看不到这些自动发送的内容。**

用户视角：

> "我还是没有看到定时发送的内容"

### ✅ 根因已定位（2026-11-05 12:18）

**代码位置**：`serial_bridge\supervisor.py` 的 `poll()` 方法（约 538 行）

```python
def poll(self, force=False):
    # 只有 watch 模式才取循环数据
    if self.mode == "watch" and self.loop.running:
        data = self.loop.take()
        return {...}
    
    # 轻模式：完全不碰串口
    if not force:
        return {"ok": True, "rx_text": "", ...}   # ← 永远返回空！
```

**因果链**：

```
1. 定时发送在 light 模式下运行（watch_running=True）
2. 数据确实收到了，存在 self.loop 的缓冲区里
3. 但 poll() 判断条件写的是 mode == "watch"
4. 当前 mode == "light" → 走 else 分支 → 返回空字符串
5. 网页轮询拿到空 → 显示不了
```

**逻辑矛盾**：

| 配置 | 发送 | 回显显示 |
|---|---|---|
| `light` + `send_enabled: true` | ✅ 正常 | ❌ **不显示** |
| `watch` | ✅ 正常 | ✅ 正常 |

**定时发送在 light 模式下应该也能看到回显，否则这个功能没意义。**

### 修复方案

把判断条件从"模式是 watch"改成"循环在跑且有数据"：

```python
def poll(self, force=False):
    # 只要有循环在跑（不管 light 还是 watch），都取数据
    if self.loop.running and self.loop.has_data():
        data = self.loop.take()
        return {
            "ok": True,
            "rx_text": data.decode("utf-8", errors="replace"),
            "rx_hex": " ".join("%02X" % b for b in data),
            "bytes": len(data),
        }
    ...
```

### 要求

自动发送的数据必须**显示在网页回显区**，和手动发送一样。

### 判定标准

- 开启定时发送后，网页回显区**每 `interval_ms` 出现一组 `>> P` + 回显**
- 不需要用户手动刷新

### 用户反馈

> "刚才点自动发送，它也没有自动发送过内容"
> "我还是没有看到定时发送的内容"

**注意**：用户说"没看到"，不是"没发送"——这两者要分清。

## Bug 5 🟡 light 模式仍然占用串口

### 现象

```
mode: light
watch_running: False
但 COM10 被占用（外部程序打不开）
```

### 矛盾点

代码注释写：

> light（默认）不长期占口：每个请求临时开口 → 读 → 关。

但实测：**网页一启动，串口就被占住**，外部程序（含 `serial_send`）打不开。

### 用户影响

- 网页开着时，串口助手用不了
- 网页开着时，AI 的 `serial_send` 可能失败

### 要求

light 模式下：

- 启动时**不打开**串口
- 每个 `/send`、`/poll` 请求临时打开→操作→**立即关闭**
- 验证：网页开着时，外部程序能打开同一串口

### 注意

之前测试曾出现"不占口"的结果，后来又变"占口"。可能是：
- 句柄泄漏（未正确 close）
- 或某后台线程持有串口

### 原现象（留档）


> "发现一个问题，控制权接管虽然会在上面的小栏里展示但是串口收发内容里依旧能看到"

### 现象

点「交给AI / 人类接管」后，**同一件事出现两次**：

- ✅ 顶部状态轨道：`14:0x:xx 控制权 → AI 托管`
- ❌ 串口收发区：`-- 控制权：AI 托管`

数据区里这行和设备回显混在一起，翻历史时**分不清哪行是设备说的**。

### 根因

两条写入通道，控制权走了两条：

| 通道 | 函数 | 目标 | 是否该走 |
|---|---|---|---|
| 事件轨道 | `pushEvent()` → `#timelineList` | 顶部小栏 | ✅ |
| 数据区 | `append()` → `#console` | 串口收发区 | ❌ |

具体两处：

1. `renderStatus()` **519–522 行**：轮询发现状态变了 → `pushEvent('ctrl', ...)` ← **正确**
2. `#controlbar` 按钮回调 **623–631 行**：点完立刻 `append('-- 控制权：...')` ← **多余**

第 2 条与第 1 条完全重复：按钮回调里已经调了 `tick()`，`renderStatus()` 照样会打轨道那条。

### 同类问题（`append` 被当成通用输出，共 6 处）

| 行号 | 内容 |
|---|---|
| 624 | `-- 控制权：xxx` |
| 627/629/631 | `-- 已释放串口 / 已重新占用 / 串口未能重新占用` |
| 651 | `-- 已切到监视模式（占口）` |
| 693 | `-- 已重连 COM7 @ 115200` |
| 706/708/710 | `-- 已暂停并释放串口 / 已重新占用 / 未占用串口` |
| 798/805 | `-- 规则保存失败 / 规则已保存到 xxx` |

### 要求

- `append()` **只许写真实收发字节**（`>> 命令` + 回显）
- 系统事件一律走事件轨道，不设例外

### 附带发现（优先级更高的真 bug）

`send()` **588 行**：命令**先打到界面、再发出去**。

```js
append('>> ' + shown + '\n');        // 先无条件打印
post('/send', ...).then(function (data) {
  if (!data.ok) { append('!! ' + errText(data.error) + '\n'); return; }
```

发送被拒（`control_blocked`、串口被占、格式错）时，界面**照样有 `>> 命令`**，
看起来像发出去了，实际设备没收到 → "我明明发了设备没反应"。

**要求**：发送成功后才打印 `>> 命令`；失败的只进轨道标红。

### 判定标准

```
1. 点「交给AI」→ 轨道出现「控制权 → AI」，数据区【无】任何 -- 控制权 字样
2. 发 P → 数据区只有 >> P 和 STATE RUNNING，无杂项
3. 拔掉设备发命令 → 数据区【不出现】>> 命令（只有轨道红字）
4. 清空按钮仍只清数据区、保留轨道
```

## Bug 7 ✅ 异常判定不触发（规则不执行）—— 已修复

> 2026-11-05 12:28 实测确认；**2026-11-05 13:58 回归通过**
> **与 Bug 4 是同类问题**——都是"数据有了，但处理链路没走到"

### ✅ 根因（开发方定位）

两条独立原因叠加：

1. **`WebServer.send()` 从来没调用过 `_maybe_check`** —— 手动发的命令根本不进判定流程。
   判定只在监视模式的读线程里跑，所以"手动发命令 → 回 FAULT → alerts 空"。
2. **异步 `[FAULT]` 被截断** —— 底盘在 `OK 4 TARGETS` 之后约 424ms 才异步报 `[FAULT]`，
   而当时 `quiet_ms=200`，收帧窗口早就关了，FAULT 那半句根本没读进来。

### ✅ 修复

- `send()` 里补 `self._maybe_check(result["rx_text"], "manual")`

### 原现象（留档）

配置了 `check_enabled=true`、`check_source=both`，规则里明确写了：

```json
{
  "name": "堵转保护触发",
  "when": { "type": "contains", "value": "FAULT" },
  "then": { "send": "R", "max_retries": 3 },
  "notify": true
}
```

实测：

```
1. 设置 check_enabled=True, check_source=both   → 设置成功
2. 手动发 W 1000 1000 1000 1000
3. 设备返回 [FAULT] stall mask=15  send R to reset    ← 确实出现了 FAULT
4. 查 /status → alerts: []                            ← 但告警列表空的！
```

**规则应该匹配到 `FAULT` 并自动发 `R`，但完全没动静。**

### 已排除的可能

| 可能 | 排除依据 |
|---|---|
| 规则配置缺失 | ❌ 配置文件里规则确实存在 |
| 触发条件不满足 | ❌ 设备确实返回了 `FAULT` 字符串 |
| 开关没开 | ❌ `/status` 确认 `check_enabled: true` |
| 判定来源不对 | ❌ 试过 `both` 和 `watch_only` 都不行 |

### 排查方向

1. **判定逻辑是否根本没被调用**——`check_enabled` 变了之后，有没有真正启动判定流程
2. **是否和 Bug 4 同源**——Bug 4 是 `poll()` 在 light 模式下不取数据；判定可能也依赖同一个数据源，导致"没数据可判"
3. **规则匹配是否执行**——`contains: FAULT` 的匹配逻辑有没有跑
4. **告警写入是否失败**——即使匹配了，`alerts` 可能写入失败但没报错

### 关键线索

**Bug 4 的根因是 `poll()` 判断 `mode == "watch"` 才取数据。**

如果判定流程也走 `poll()` 的数据，那 **light 模式下判定永远拿不到数据 → 永远不触发**。

**建议**：检查判定流程的数据来源，是否与 `poll()` 共用同一个被 mode 卡住的分支。

### 要求

- `check_enabled=true` 时，无论 light 还是 watch 模式，判定都必须工作
- 规则匹配后，`alerts` 要有记录
- 自动处置命令要真正发出（受白名单限制）

### 判定标准

```
1. 开 check_enabled，制造 FAULT
2. /status 的 alerts 里出现一条记录，含：
   - 规则名
   - 匹配到的内容
   - 执行的动作
3. 如果配了 then.send，设备应收到该命令
```

## Bug 8 ✅ AI 发的命令网页看不到（人机信息不对称）—— 已修复

> 2026-11-05 12:30 用户反馈 + 实测确认；**2026-11-05 13:56 回归通过**

### 用户反馈

> "刚才你发新消息了吗？这边看不到"

### 实测证据

日志里确实有 AI 发的命令：

```
[12:27:18] TX A
[12:27:18] RX ERR STATE
[12:27:19] TX W 1000 1000 1000 1000
[12:27:19] RX OK 4 TARGETS
[12:27:19] RX [FAULT] stall mask=15  send R to reset
[12:27:21] TX R
[12:27:21] RX OK RESET
```

**但用户在网页回显区看不到这些。**

### 根因

**两条独立的发送路径：**

| 路径 | 谁用 | 网页能看到 |
|---|---|---|
| 网页 `/send` | 用户点按钮 | ✅ 能（自己发自己显示） |
| 插件 `serial_send` | AI 调用 | ❌ **看不到**（不经过网页） |

```
AI 的 serial_send → 直接开串口 → 发 → 关 → 写 log.txt
                          ↓
                   网页服务没参与
                          ↓
                   网页回显区不显示
```

**日志是共享的**（都在 `log.txt`），但**网页回显区只显示它自己收到的东西**。

### 影响

用户最初的核心需求是"**你发命令、我也发命令，双方都能看到**"。现在：

- ✅ AI 能看到用户发的（读日志）
- ❌ **用户看不到 AI 发的**（网页不显示）

**信息不对称，违背人机协同的初衷。**

### 解决方案（二选一）

#### 方案 A：网页定时读日志增量

网页每隔 N 秒读一次 `log.txt` 的增量，追加到回显区。

| 优点 | 缺点 |
|---|---|
| 实现简单 | 有延迟 |
| 不改架构 | 可能与手动发送的显示混在一起 |

#### 方案 B：AI 发送统一走网页服务（推荐）

AI 发命令时不直接开串口，而是调用网页的 `/send` 接口。

```
AI 调 serial_send
    ↓
检测网页服务是否在跑
    ├── 在跑 → 调 POST /send（网页显示 + 写日志）
    └── 没跑 → 自己开串口（原逻辑）
```

| 优点 | 缺点 |
|---|---|
| 真正统一，双方实时看到 | 需要网页服务运行 |
| 符合人机协同初衷 | 增加一次 HTTP 调用 |

### ✅ 采纳方案 B，并已实测通过（2026-11-05 13:56）

`cli.py` 里加了 `_forward_to_web()`：CLI/AI 发命令前先读
`.serial-logs/.runtime/state/<scene>.web.json` 拿到网页地址，
在跑就 `POST /send`（带 `source: "ai"`），网页把这一帧记进 `auto_frames`，
`/poll` 返回时带 `frames`，回显区就能看到；网页没跑就回退到直接开串口。

**回归实测**：

```
$ bridge.py send --scene 蓝牙AT --command P --as ai
{"ok":true,"port_source":"web","response":"STATE RUNNING\r\nCH1 T=0 ..."}

$ GET /poll
{"ok":true,"frames":[{"tx":"P","rx":"STATE RUNNING\r\n...","bytes":99,
                      "source":"ai"}]}
```

帧带 `source: "ai"`，前端据此标 `[AI]`，判定标准三条全过。

> ⚠️ 测试注意：网页每 700ms 自动 `/poll` 一次，会**先把帧取走**。
> 手工验证时如果网页开着，"AI 发完立刻 poll"可能扑空（帧已被前端吃掉），
> 这**不是 bug**——正确的验证方式是看网页回显区，或者先把网页窗口关掉/暂停轮询。
