## 二、整体架构（一图看懂）

```
┌─────────────────────────────────────────────────────────────┐
│  DSH（AI 宿主）                                              │
│    ↓ 调用工具                                                │
│  index.js  ← 注册 8 个工具，每次 spawn 一个 Python 子进程      │
└────────────────────────┬────────────────────────────────────┘
                         ↓ 命令行（stdout 一行 JSON）
┌────────────────────────┴────────────────────────────────────┐
│  Python 内核（serial_bridge/）                                │
│                                                              │
│  cli.py  ← 命令行入口，解析参数、分发到各 cmd_* 函数            │
│    ├── 有管家 → 转发给 daemon.py 的 HTTP                     │
│    ├── 有网页 → 转发给 supervisor.py 的 HTTP                 │
│    └── 都没有 → 自己开关串口（io.py / transport.py）          │
│                                                              │
│  ┌──────────────┬──────────────┬──────────────┐             │
│  ↓              ↓              ↓              ↓             │
│ transport.py   ports.py      rules.py      state.py         │
│ （收发）        （找端口）     （判定）       （共享状态）      │
│                                                              │
│  ┌──────────────────────────────┐                           │
│  │ daemon.py（管家，常驻进程）    │ ← 独立进程，HTTP 8898      │
│  │ supervisor.py（网页，可选）    │ ← 独立进程，HTTP 8898/8897 │
│  └──────────────────────────────┘                           │
└─────────────────────────────────────────────────────────────┘
```

**三个关键设计**：
1. **AI 和硬件之间只有一条路** —— 都经过 `transport.py`，没有旁路
2. **管家和网页互斥但可共存** —— 网页检测到管家就让位（不抢口）
3. **业务逻辑不认识设备** —— 设备知识全在 `protocols/` 里

## 三、Python 内核（`serial_bridge/`）

### 3.1 `transport.py` — 传输层（255 行）

**职责**：所有"怎么把字节发出去、怎么收回来"的逻辑。**这是扩展新通信方式的入口。**

| 类/函数 | 行号 | 作用 |
|---|---|---|
| `Transport` | 20 | **抽象基类**，定义 open/close/write/read/describe |
| `SerialTransport` | 76 | 串口实现（pyserial），**打开后自动置 DTR/RTS 低** |
| `_load_serial()` | 164 | 加载 pyserial（找不到时报友好错误） |
| `_classify_open_error()` | 179 | 把 pyserial 的异常分类成"被占用/不存在/其他" |
| `register_transport(kind, cls)` | 215 | **注册新传输方式**（加 TCP 时用） |
| `create_transport(cfg)` | 220 | **工厂**：按 `cfg["transport"]` 创建对应实例 |
| `describe_transport(cfg)` | 238 | 给网页显示用：`{type, device, baud, frame, status}` |

**要加 TCP/CAN 怎么办**：
```python
# 1. 写一个类
class TcpTransport(Transport):
    def open(self): ...
    def write(self, data): ...

# 2. 注册
register_transport("tcp", TcpTransport)

# 3. 场景配置加一行
{"transport": "tcp", "host": "192.168.1.1", "port": 8080}
```
**业务层一行不用改。**

### 3.2 `ports.py` — 端口发现（215 行）

**职责**：枚举系统串口、按配置匹配到具体端口。

| 函数 | 行号 | 作用 |
|---|---|---|
| `scan_ports()` | 33 | 枚举所有串口（含 VID:PID、描述） |
| `resolve_port(cfg)` | 104 | **核心**：三级匹配，返回 `{device, source, note}` |
| `_match_by_vid_pid()` | 68 | 第一级：VID:PID 精确匹配（最可靠） |
| `_match_by_description()` | 75 | 第二级：描述模糊匹配（如 "CH340"） |
| `_match_by_device()` | 91 | 第三级：精确 COM 号 |
| `_port_sort_key()` | 53 | 排序：COM10 排在 COM9 后面（不是字典序） |
| `_ambiguous()` | 207 | 匹配到多个时报错，列出候选让用户选 |

**为什么总是先扫描**：COM 号会变（CH340 在 COM7/COM10 之间跳过三次），
所以即使配置写了 `com`，也要先扫描确认。

### 3.3 `rules.py` + `rule_checker.py` — 规则引擎（197 + 108 行）

**职责**：判断回显内容是否命中规则，命中后执行动作。

**`rules.py`**（纯逻辑，无副作用）：

| 类/函数 | 行号 | 作用 |
|---|---|---|
| `RuleEngine` | 55 | 规则匹配引擎 |
| `RuleResult` | 33 | 匹配结果（规则名、原因、动作） |
| `allowlist_check()` | 195 | 白名单校验（自动命令必须在此列表内） |

**`rule_checker.py`**（带副作用的封装）：

| 类 | 行号 | 作用 |
|---|---|---|
| `RuleChecker` | 14 | **网页和管家共用**：处理开关判断、熔断、告警写入 |

**⚠️ 重要历史**：`RuleChecker` 是 2026-11-06 才抽出来的。
之前 `WatchLoop` 和 `Daemon` 各写了一份判定逻辑，**导致管家模式下 `no_response` 规则失效**
（因为管家那份忘了传 `no_response_streak`）。
**现在两边都只调 `RuleChecker.run(text, source, streak)`。**

**支持的判据类型**：
- `contains` — 回显包含某字符串
- `regex` — 正则匹配
- `no_response` — 连续 N 次无回显

### 3.4 `port_manager.py` — 端口管理（151 行）

**职责**：决定"现在该不该占着串口"。

| 类 | 行号 | 作用 |
|---|---|---|
| `PortManager` | 19 | 端口占用/释放/收敛/看门狗/占用者查询 |

**核心逻辑**：控制权和串口占用是**两件事**
- `control = ai` → 网页/管家持有句柄
- `control = human / paused` → **立刻关闭句柄**，让串口助手能用

**为什么单独一个文件**：这段逻辑有三个调用路径（网页按钮、CLI、工具），
如果写在网页里，另外两条路径改了状态网页不知道（Bug 3 就是这么来的）。

## 六、场景配置（`protocols/`）

**每个场景一个目录**，里面两个文件：

```
protocols/<场景名>/
├── config.json     机器读的（串口参数、规则、白名单）
└── protocol.md     人/AI 读的（命令表、踩坑记录）
```

**现有场景**：

| 场景 | 用途 | 端口匹配 |
|---|---|---|
| `蓝牙AT` | HC-05 + gcSTM32 底盘 | `match: CH340` |
| `Modbus从站` | Modbus RTU 从站 | `VID:PID 1A86:7523` |
| `文字游戏` | 空配置模板 | 无（示例用） |

**加新设备 = 新建一个目录**，不用改代码。

**`config.json` 关键字段**：

| 字段 | 作用 |
|---|---|
| `transport` | 传输类型（默认 `serial`） |
| `com` / `match` / `match_vid_pid` | 端口匹配（三级） |
| `baud` / `newline` | 串口参数 |
| `quiet_ms` | 收尾等待（等异步故障） |
| `wait_first_byte_ms` | 等首字节上限 |
| `watch.rules` | 判定规则 |
| `watch.allowed_auto_commands` | 自动命令白名单 |

## 八、数据流（一次 `serial_send` 的完整路径）

```
AI 调 serial_send
    ↓
index.js  resolvePython() → 找到 Python
    ↓
spawn: python bridge.py send --scene 蓝牙AT --command P --as ai
    ↓
cli.py    cmd_send()
    ├── _forward_to_daemon()  ← 管家在跑？
    │       ↓ 是 → HTTP POST 127.0.0.1:8898/send
    │              ↓
    │           daemon.py  Daemon.send()
    │              ├── 检查控制权（state.py）
    │              ├── transport.write(帧)
    │              ├── 等回显（JUDGE_WINDOW_S）
    │              └── RuleChecker.run()  ← 规则判定
    │
    └── 否 → _forward_to_web()  ← 网页在跑？
            ├── 是 → HTTP POST /send
            └── 否 → io.py transact()  ← 自己开关串口
    ↓
返回一行 JSON 给 index.js
    ↓
AI 收到结果
```
