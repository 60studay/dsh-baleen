# 串口桥插件 · 自检提示词

> 用途：**直接复制给 AI 执行**，让它按步骤验证插件是否正常工作
> 更新日期：2026-11-04 23:30

---

## 使用方法

把下面 `===` 之间的内容整段复制，发给执行验证的 AI（它需要有文件读写和命令执行能力）。

---

```
=== 自检开始 ===

请对 <插件目录> 这个 DSH 串口插件做一次完整自检。
严格按下面 7 项执行，每项都要给出【通过/失败】和实际证据，不要跳项、不要凭印象。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【前置信息】
插件路径：<插件目录>
Python：%USERPROFILE%\AppData\Local\Programs\Python\Python312\python.exe
测试场景：蓝牙AT（硬件：CH340 + HC-05，串口号会变，靠 match=CH340 自动匹配）
如果硬件没插，第 3、4 项标记为"跳过"，其余项照测。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 1 项：代码通用性（最重要）】

在插件代码里搜索以下字符串，确认是否出现：
  - 具体命令字："P"、"AT"、"W "、"A"、"X"
  - 故障字：FAULT、stall、ERROR
  - 数据格式：CH1、T=、A=

执行：
  grep -rn 'FAULT\|stall\|CH[0-9]' <插件目录>\serial_bridge\
  grep -rn '"P"\|"AT"' <插件目录>\serial_bridge\

判定标准：
  ✅ 通过 = 这些字符串只出现在注释、文档字符串、或从配置读取的变量名里
  ❌ 失败 = 出现在实际的判断逻辑/硬编码的命令里

输出：列出每个命中位置，并说明它是否属于"硬编码"。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 2 项：控制权是否真正生效（安全底线）】

这是之前确认的严重 bug，必须验证。

步骤：
  a) 切到 ai 状态，发一条命令 → 应该成功
  b) 切到 pause 状态，发一条命令 → 应该【被拒绝】
  c) 切到 human 状态，发一条命令 → 应该【被拒绝】

执行（用 CLI）：
  $py = "%USERPROFILE%\AppData\Local\Programs\Python\Python312\python.exe"
  $b = "<插件目录>\bridge.py"

  & $py $b control --scene 蓝牙AT --action ai
  & $py $b send --scene 蓝牙AT --command "P"        # 期望成功

  & $py $b control --scene 蓝牙AT --action pause
  & $py $b send --scene 蓝牙AT --command "P"        # 期望失败！

  & $py $b control --scene 蓝牙AT --action human
  & $py $b send --scene 蓝牙AT --command "P"        # 期望失败！

判定标准：
  ✅ 通过 = pause 和 human 状态下，send 明确返回错误且提示"需要人类点[交给AI]"
  ❌ 失败 = pause/human 状态下 send 仍然成功

输出：三个状态各自的 send 结果（成功还是拒绝，拒绝时的错误信息）。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 3 项：串口自动匹配】

验证：配置里写死 COM 号时，实际设备在别的 COM 号，能否自动找到。

步骤：
  a) 看 protocols\蓝牙AT\config.json，确认 com 字段的值（比如 COM7）
  b) 看实际 CH340 在哪个 COM（serial_list 或 --list）
  c) 发一条命令，看返回里的 note 字段

判定标准：
  ✅ 通过 = 实际用了正确的 COM，且 note 里注明"已从 X 变为 Y"
  ✅ 通过（无需切换）= 配置的 COM 和实际一致
  ❌ 失败 = 报错说找不到串口

输出：配置的 COM、实际的 COM、返回的 note 内容。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 4 项：基本收发】

发这几条命令，确认回显正确：
  P        → 期望含 "STATE"
  H        → 期望含 "commands" 或帮助文本
  A        → 期望含 "OK RUNNING"
  X        → 期望含 "OK IDLE"

判定标准：
  ✅ 通过 = 每条都有合理回显，且返回里同时有文字和 hex
  ❌ 失败 = 无回显、或回显明显不对、或缺 hex

⚠️ 如果无回显，先别急着判定硬件故障！按这个顺序排查：

  a) 发 AT
     - 回 OK → **模块卡在 AT 模式**，跳到 (b)
     - 无回显 → 不在 AT 模式，继续查波特率/接线

  b) 发 AT+STATE?
     - CONNECTING → 正在连但没连上 ❌
     - CONNECTED  → 已连接 ✅
     - PAIRABLE   → 等待配对

  c) 如果卡在 AT 模式或 CONNECTING，按这个恢复：
     1. 发 AT+RESET
     2. **立即关闭串口**（关键！不能一直占着）
     3. 等 20 秒（期间不碰串口，让模块自己连从机）
     4. 重新打开，发 AT+STATE? 确认 CONNECTED
     5. 再发 P 测试

  d) 恢复后仍然无回显，才检查：
     - 波特率（115200）
     - 从机是否上电
     - 从机 TX/RX 是否接反（TX→PB11，RX→PB10）
     - 主机和从机距离/遮挡

**这一步很关键**：设备"已上电但无回显"最常见的原因不是硬件坏，
而是主机 HC-05 卡在 AT 模式（只做本地应答，不转发数据）。

输出：每条命令的实际返回，以及（如无回显）上面的排查结果。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 5 项：网页轻模式不占口】

验证：网页开着时，串口还能被其他程序使用。

步骤：
  a) 启动网页：& $py $b web --scene 蓝牙AT --port 8898
  b) 等 5 秒，用另一个进程尝试打开同一个 COM 口
  c) 检查是否成功

执行（打开测试）：
  & $py -c "import serial; s=serial.Serial('COM10',115200,timeout=0.3); s.close(); print('可打开')"
  （把 COM10 换成实际的串口号）

判定标准：
  ✅ 通过 = 网页开着时，串口仍可被打开
  ❌ 失败 = PermissionError / 拒绝访问

补充测试：网页开着时，用 CLI 发一条命令，确认也能成功（人机共存）。

输出：网页是否启动成功、串口是否可打开、CLI 能否同时发命令。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 6 项：错误提示友好度】

模拟三种错误，看提示是否清晰：

  a) 设备未连接
     把 match 改成一个不存在的值（如 "NONEXIST"），发命令
     期望：提示"没找到匹配的串口设备"+ 列出可用串口 + 排查步骤

  b) 串口被占用
     先占住串口（起一个网页或串口助手），再发命令
     期望：提示"被其他程序占用"+ 说明可能原因

  c) 命令无回显
     发一条设备不认识但格式合法的命令（如 "ZZZZ"）
     期望：返回"无回显"或空，但不应该抛 Python 堆栈

判定标准：
  ✅ 通过 = 三种都有中文提示，且【没有任何 Python traceback】
  ❌ 失败 = 出现 traceback / 报错不可读

输出：三种情况的完整错误信息。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【第 7 项：文件结构完整性】

确认这些文件都在：
  - bridge.py（入口）
  - index.js（插件工具注册）
  - package.json
  - cordis.patch.yml
  - serial_bridge\（内核包，含 cli.py / io.py / ports.py / rules.py / state.py / supervisor.py）
  - web\index.html
  - protocols\蓝牙AT\（config.json + protocol.md）
  - vendor\pyserial-3.5\（内置依赖）

判定标准：
  ✅ 通过 = 全部存在
  ❌ 失败 = 缺任何关键文件

输出：列出缺失的文件（如有）。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
【最终报告格式】

请按这个格式输出：

## 自检结果

| # | 项目 | 结果 | 证据摘要 |
|---|---|---|---|
| 1 | 代码通用性 | ✅/❌/跳过 | ... |
| 2 | 控制权生效 | ✅/❌/跳过 | ... |
| 3 | 串口自动匹配 | ✅/❌/跳过 | ... |
| 4 | 基本收发 | ✅/❌/跳过 | ... |
| 5 | 网页不占口 | ✅/❌/跳过 | ... |
| 6 | 错误提示 | ✅/❌/跳过 | ... |
| 7 | 文件结构 | ✅/❌/跳过 | ... |

### 发现的问题
（逐条列出，标注严重程度：🔴严重 / 🟡中等 / 🟢轻微）

### 总结
- 通过 X/7
- 是否可以进入下一阶段开发：（是/否 + 理由）

=== 自检结束 ===
```

---

## 自检后的判断

| 结果 | 下一步 |
|---|---|
| **7/7 通过** | ✅ 可以进入阶段 2（AI 侧增强） |
| **第 1、2 项通过，其他有小问题** | ⚠️ 可以开始阶段 2，但要记录遗留问题 |
| **第 1 或第 2 项失败** | 🔴 **停止**，必须修完再继续 |

**为什么第 1、2 项是硬门槛**：

- **第 1 项（通用性）** 失败 → 插件退化成一次性脚本，失去存在意义
- **第 2 项（控制权）** 失败 → 人机协同不安全，可能造成硬件损坏

---

## 补充：如果某项失败怎么排查

| 失败项 | 排查方向 |
|---|---|
| 1 通用性 | 搜索命中位置，看是注释还是逻辑；逻辑里硬编码的必须改成读配置 |
| 2 控制权 | 检查 `serial_send` 执行前有没有 `get_control_state()` 判断 |
| 3 自动匹配 | 检查 `ports.py` 的匹配顺序；确认 `match` 字段被读取 |
| 4 基本收发 | 检查硬件连接、波特率、`newline` 配置 |
| 5 网页不占口 | 检查 `web_mode` 是否在启动时就 `serial.Serial()` 了 |
| 6 错误提示 | 检查 `errors.py` 是否把所有异常都包装成了中文 |
| 7 文件结构 | 对照清单逐个确认 |
