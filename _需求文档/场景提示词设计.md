# 场景提示词（prompt.md）设计

> 编写日期：2026-11-04
> 针对版本：`<插件目录>\`
> 目标：让 AI 在**新会话**里立刻知道"这个场景该怎么操作"

---

## ⚠️ 铁律：通用性优先

提示词是**纯文本，按场景存放**，插件不解析其内容。

| 必须 | 禁止 |
|---|---|
| 提示词存在场景目录的 `prompt.md` | 把提示词写进插件代码 |
| `serial_info` 原样返回 | 插件尝试"理解"或解析提示词 |
| 每个场景独立 | 全局共用一份 |

---

## 一、要解决的问题

### 现状

AI 换到新会话时，只知道：
- 串口参数（`config.json`）
- 协议档案（`protocol.md`）——命令表、返回值含义、踩坑记录

### 缺失的部分

**"该怎么操作"** —— 也就是**操作顺序、前置条件、禁忌**。

举例（底盘场景）：

| 知识类型 | 现在有吗 | 存在哪 |
|---|---|---|
| `P` 命令返回什么 | ✅ 有 | `protocol.md` |
| `FAULT` 是什么意思 | ✅ 有 | `protocol.md` |
| **发运动命令前必须先 `A` 启动** | ❌ **没有** | 缺 |
| **调参时速度别超 500** | ❌ **没有** | 缺 |
| **出 FAULT 要先 `R` 清除** | ⚠️ 部分有 | 散落在 protocol.md |

**这些"操作纪律"如果不写下来，每个新会话的 AI 都要重新摸索，甚至踩坑。**

---

## 二、设计

### 2.1 文件位置

```
protocols\<场景名>\
├── config.json      串口参数 + watch 配置
├── protocol.md      协议档案（命令表、返回值、踩坑）
└── prompt.md        ★操作提示（本文档新增）
```

### 2.2 格式：纯 Markdown，无强制结构

**不规定固定 schema**，因为不同设备的操作纪律差别很大。建议包含：

```markdown
# <场景名> 操作提示

## 前置条件
- 发运动命令前必须先发 <启动命令>
- 确保轮子架空 / 设备已上电

## 常用操作顺序
1. <步骤一>
2. <步骤二>
3. <步骤三>

## 安全限制
- 速度不要超过 <值>
- 单次运行不要超过 <时长>

## 异常处理
- 出现 <某状态> → 先发 <某命令>

## 禁止操作
- 不要 <某操作>（原因）
```

### 2.3 加载方式

**`serial_info` 返回时一并带上 `prompt.md` 内容。**

返回结构：

```json
{
  "scene": "蓝牙AT",
  "serial": { "port": "COM10", "baud": 115200 },
  "protocol": "<protocol.md 全文>",
  "prompt": "<prompt.md 全文>",
  "promptMissing": false
}
```

**如果 `prompt.md` 不存在**：`prompt` 为空，`promptMissing: true`，不报错。

### 2.4 不解析、不强制

| 要求 | 说明 |
|---|---|
| **原样返回** | 插件不解析 markdown 结构 |
| **可选** | 没有 `prompt.md` 也能正常工作 |
| **纯文本** | 不做任何模板替换 |

## 三、示例

### 示例 1：STM32 底盘（有严格操作纪律）

```markdown
# 蓝牙AT（STM32 底盘）操作提示

## 前置条件
- 发任何运动命令前，必须先发 `A` 启动（IDLE → RUNNING）
- 未启动时发 `W` 会返回 `ERR NOT RUNNING`
- 桌面测试必须架空轮子

## 常用操作顺序
1. `X` —— 先确保停车（IDLE）
2. `A` —— 启动闭环
3. `W <s1> <s2> <s3> <s4>` —— 设四路速度
4. `P` —— 确认状态和实际速度
5. `X` —— 结束，退出闭环

## 安全限制
- 首次调试速度不要超过 500（满值 1000）
- 单次连续运行不超过 30 秒
- 出现任何异常立即发 `X` 停车

## 异常处理
- 出现 `[FAULT] stall mask=N` → 先发 `R` 清除，再排查
- 发命令无回显 → 检查蓝牙连接和波特率（应为 115200）

## 禁止操作
- 不要在未接电机时长时间给速度（会一直报堵转）
- 不要跳过 `A` 直接发 `W`
```

### 示例 2：蓝牙模块 AT（较宽松）

```markdown
# 蓝牙AT 模块操作提示

## 前置条件
- 模块进入 AT 模式后才能响应 AT 命令
- AT 波特率与数据波特率一致（本模块为 115200）

## 常用操作
1. `AT` —— 测试连通，回 `OK` 说明正常
2. `AT+UART?` —— 查当前波特率
3. `AT+ROLE?` —— 查主从角色

## 注意
- 改 `AT+UART` 后，AT 命令的波特率也会跟着变
- `AT+ORGL` 会恢复出厂设置（波特率回 38400、角色回从机），**慎用**
- 链路建立后，AT 命令会被当数据转发，属正常

## 禁止操作
- 不要在配对成功后继续发 AT 配置命令
```

### 示例 3：Modbus 从站（无特殊纪律）

```markdown
# Modbus从站 操作提示

## 说明
- 标准 Modbus RTU 协议，从站地址 0x01
- 查询命令：`01 03 00 00 00 01 84 0A`
- 回显为十六进制字节流

## 注意
- 需要 CRC 校验
- 建议用 hex 模式查看回显
```

## 四、与其他文件的分工

| 文件 | 内容 | 谁读 | 性质 |
|---|---|---|---|
| `config.json` | 串口参数、watch 配置 | 插件解析 | **机器可读** |
| `protocol.md` | 命令表、返回值含义、踩坑记录 | AI 阅读 | **参考手册** |
| `prompt.md` | 操作顺序、前置条件、禁忌 | AI 阅读 | **行为约束** |

**一句话区分**：
- `protocol.md` = **"这个设备能做什么"**
- `prompt.md` = **"用这个设备时该注意什么"**

## 五、实现要求

### 5.1 `serial_info` 增强

```
读取顺序：
1. 读 config.json → 串口参数
2. 读 protocol.md → protocol 字段
3. 读 prompt.md → prompt 字段（不存在则 promptMissing: true）
4. 全部原样返回
```

### 5.2 其他工具是否也返回 prompt？

| 工具 | 是否返回 prompt | 理由 |
|---|---|---|
| `serial_info` | ✅ **返回** | 这是"了解场景"的主入口 |
| `serial_send` | ❌ 不返回 | 每次发命令都返回提示词太啰嗦 |
| `serial_status` | ❌ 不返回 | 状态查询不需要 |
| `serial_list` | ❌ 不返回 | 只列场景名 |

**建议**：只在 `serial_info` 返回，保持其他工具输出简洁。

### 5.3 AI 的推荐行为（写进插件 description）

在 `serial_info` 的工具描述里加一句：

> "首次使用某个场景前，先调用 serial_info 了解操作纪律（prompt 字段），
> 再开始发命令。"

这样 AI 会自觉先看提示词。

### 5.4 新建场景时自动生成模板

`serial_scene_create`（如果实现了）创建场景时，自动生成空的 `prompt.md` 模板：

```markdown
# <场景名> 操作提示

## 前置条件

## 常用操作顺序

## 安全限制

## 异常处理

## 禁止操作
```

**让用户/后续 AI 直接往里填。**

## 六、验收清单

### 基础功能
- [ ] `serial_info` 返回 `prompt` 字段
- [ ] 有 `prompt.md` 时内容完整返回
- [ ] 无 `prompt.md` 时 `promptMissing: true`，不报错
- [ ] 提示词内容原样返回，不被解析或改写

### 通用性
- [ ] 提示词内容来自文件，**代码里无任何设备相关文字**
- [ ] 换场景时返回对应场景的提示词
- [ ] 新建场景能生成模板

### 与其他文件协同
- [ ] `config.json` / `protocol.md` / `prompt.md` 三者独立
- [ ] 任一文件缺失都不影响其他功能

## 七、为什么这很重要

用户最初的核心诉求：

> "我不能每要用一次都去新会话里，让他重新复制一份过去"
> "让读取使用说明的 AI 去教当时使用这 AI 的用户"

`prompt.md` 正好解决这个：

| 场景 | 效果 |
|---|---|
| 新会话开始 | AI 调 `serial_info` → 读到 `prompt.md` → **立刻知道怎么操作** |
| 用户换设备 | 只需给新设备写一份 `prompt.md` |
| 多场景并存 | 每个场景有独立提示词，互不干扰 |

**这是"让 AI 真正会用这个工具"的最后一环。**

---

## 八、给开发者的话

`prompt.md` 的设计极其简单——**就是读一个文本文件、原样返回**。

**不要做以下事情**：
- ❌ 不要解析 markdown 结构
- ❌ 不要做模板变量替换
- ❌ 不要把提示词合并进 `protocol.md`
- ❌ 不要在代码里写任何默认提示词内容

**保持"哑传输"**：读文件 → 返回内容。这样它永远是通用的。
